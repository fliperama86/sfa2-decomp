## The do-while wrapper is an accepted stand-in; func_801427d8 exact (2026-10-11)

- The owner's decision. Shown that a function one instruction away from
  the original becomes byte-identical when a group of its statements
  stands in a `do { } while (0)`, and asked whether such a function may
  be published as identical "with a comment marking the wrapper as an
  inferred macro shape", he first asked where the rule against it came
  from (the matching guide, "anything whose only purpose is to steer the
  compiler"), and then answered: "yes, allow the wrapper with the
  comment".
- The guide (`ps1/docs/matching-guide.md`) gets two additions. "What is
  allowed": the wrapper as a second accepted stand-in, its fixed comment,
  and the rules for its use (the smallest group of whole statements that
  belongs together; the function in its plainest form inside and around
  it; the measurement without the wrapper in the pull request). "What
  this compiler does": the order of global allocation and the two rules
  that move it without changing an instruction.
- The two rules, read in GCC 2.6.3's source. `global.c`,
  `allocno_compare`: values that live across basic blocks are taken in
  the order of `floor(log2(refs)) * refs / length of life`, the highest
  first. `flow.c`: `reg_n_refs[regno] += loop_depth`, so a reference in
  a loop counts more; a `do { } while (0)` makes no loop code but its
  loop note stays. `local-alloc.c`, `update_equiv_regs`: a register set
  exactly once by an instruction with a constant `REG_EQUAL` note has
  its length of life doubled.
- What was measured, in the compiler's dumps of `func_801427d8` (the
  unit's own preprocessed file, `cc1 -O2 -G0 -dl -dg`). Without the
  wrapper: no loop note; the limit `used 7 times across 40 insns` (2 x
  7 / 40 = 0.35), the halfword read from the object `used 3 times
  across 6 insns` (0.5); order of allocation `82 75 72 106 74 71`.
  With the wrapper: one `NOTE_INSN_LOOP_BEG`; the limit `used 9 times
  across 40 insns` (3 x 9 / 40 = 0.675); order `82 72 75 74 106 71`.
  The two assignments of the limit inside the wrapper are what counts
  twice. The doubling of a constant's length was read in the source and
  seen as lengths of 144 and 104 in the dump of another function
  (`func_8001a69c_slot28`, not in this change); the halves were not
  measured apart.
- `func_801427d8` (208 bytes, resident): unit `d58e50_r2`, exact:
  `baseline 208 bytes at 0x801427d8, built 208 bytes at 0x801427d8, 0
  differing instruction slots: IDENTICAL`. The wrapper stands around the
  if/else chain that picks the limit from the mode. The same source
  without the wrapper: 10 differing instruction slots (the limit and the
  halfword in each other's registers). Other forms measured on the way
  to the plainest one: the mode as `u16` without casts, 4 slots and 204
  bytes; the mode as `u16` with a cast to `s16` at eight of the ten
  comparisons, identical (the candidate's form; `s16 mode` without casts
  is the same code and plainer); the limit as `int`, 3 slots and 200
  bytes; the halfword as `int`, 1 slot; the level set to 0 at its
  declaration, 12 slots and 212 bytes; the level as `s16`, identical
  (kept `int`); the wrapper around the statements after the chain
  instead, 10 slots.
- The function leaves `ps1/src/resident_nonmatching/`, as that folder's
  page says a function does when it is rebuilt exactly: its three files
  are deleted and its five lines of the folder's README taken out. Its
  line leaves `symbols.ld`. No other function of the folder was run
  again.
- The inventory (`ps1/inventory/game.tsv`, regenerated by
  `coveragemap.py sweep`) changes in two rows: `801427d8` gets its name,
  and so does `80119444`, which commit `8ca28d7` made a unit without
  the sweep.
- How it was found. The six closest functions of the resident program
  and its modules each went to a worker for a bounded try; none came
  back exact. The rule was then read at top level from the dumps of one
  of them, predicted where a wrapper had to stand, and the prediction
  held on the first build. A private search that wraps every run of
  consecutive statements of a function and scores each variant found
  this function's wrapper (26 of 77 positions exact). The decomp
  permuter had not, because the option that inserts such blocks is
  switched off in the project's settings for it.
- Not claimed: that the original source had a macro or a block there.
  An exact build with the wrapper shows that this source is compatible
  with the original's bytes.
